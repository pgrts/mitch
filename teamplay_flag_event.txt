Confirmation: teamplay_flag_event Enum & StructureYou are correct on both counts. The standard Source Engine (TF2) definitions align with the list you "usually see," and the teamplay_flag_event structure indeed lacks a direct flag identifier.1. Enum Values (eventtype)In the standard TF2 tf_shareddefs.h, the eventtype values are defined as follows. If a list has 3 and 5 swapped, it is likely incorrect or using a non-standard mapping.ValueEvent TypeDefinition1TF_FLAGEVENT_PICKUPFlag has been picked up.2TF_FLAGEVENT_CAPTUREFlag has been captured.3TF_FLAGEVENT_DEFENDFlag has been defended (e.g., carrier killed).4TF_FLAGEVENT_DROPPEDFlag has been dropped.5TF_FLAGEVENT_RETURNEDFlag has returned to base.2. Event Data StructureThe teamplay_flag_event does not contain the flag's entity index (index or entindex). This is a known limitation when handling multiple flags (e.g., in Mannpower or custom modes).Structure:Code snippet"teamplay_flag_event"
{
    "player"    "short"     // EntIndex of the player involved (e.g., who picked it up)
    "carrier"   "short"     // EntIndex of the carrier (if applicable)
    "eventtype" "short"     // Enum 1-5 (as above)
    "home"      "byte"      // 1 if the flag was at home, 0 otherwise (only for PICKUP)
    "team"      "byte"      // Team index the flag belongs to
}

Recommended Fix for flagspawn.nutSince event_data.index will return null or throw an error, you cannot rely on this event alone to identify which specific flag instance was interacted with if you have multiple flags.You must drive the logic via the item_teamflag entity outputs, as they execute within the scope of the specific flag entity:OnReturn: Fire a VScript hook (e.g., self.GetScriptScope().MyReturnFunction()).OnCapture: Similarly, hook into the capture output.OnPickup: Can pass the activator (the player) to your script to link the player to the specific flag instance.
